Mixture of Experts

A dense model uses every parameter on every token. A mixture of experts keeps many parallel copies of the feed-forward layer and routes each token to a handful of them, so total parameters and per-token compute stop being the same number. That decoupling is the whole point — and it turns a modelling problem into a load balancing problem, because a router left to its own devices will send almost everything to a few favourite experts.

What you should walk away with

  • Parameters and FLOPs come apart. A model can hold 600B parameters and spend 30B worth of compute per token. Capacity scales with the former; inference cost with the latter.
  • The router collapses without help. Slightly-better experts get more tokens, train faster, get better, and take more tokens. An auxiliary load-balancing loss exists purely to break this feedback loop, and it is fighting the main objective.
  • Memory, not compute, is the constraint. All experts must be resident even though most are idle for any given token. MoE trades cheap FLOPs for expensive VRAM, which is why it favours large-batch server deployment over local inference.
  • The experts are not interpretable specialists. Despite the name, routing correlates with surface features like token identity far more than with topic or domain. “The physics expert” does not exist.
Tier 1 · Intuition

Plain language. No equations, no prerequisites.

A hospital, not a generalist

Section titled “A hospital, not a generalist”

A small clinic has one doctor who handles everything. Every patient sees them, and their knowledge is bounded by what one person can hold.

A hospital has a hundred specialists plus a triage nurse. Each patient sees two of them. The institution’s total expertise is enormous; the cost of treating any one patient is still two consultations.

That is a mixture of experts. The triage nurse is the router. The specialists are the expert networks. And the key economic fact is that the hospital’s capacity grew a hundredfold while the cost per patient stayed flat.

What this buys, precisely

Section titled “What this buys, precisely”

Scaling a dense transformer means every added parameter costs compute on every single token, forever, in training and in inference. That coupling is what makes frontier models expensive.

MoE breaks it. Mixtral 8×7B holds roughly 47 billion parameters and activates about 13 billion per token. You are paying 13B-model inference prices for something with considerably more than 13B worth of stored knowledge.

The bill arrives as memory

All 47B parameters must sit in memory even though only 13B are used per token — you do not know in advance which experts a token will need. So MoE saves compute and spends VRAM. This is a good trade in a datacentre with big batches and a bad one on a laptop, which is exactly the deployment pattern you see.

The problem nobody anticipates

Section titled “The problem nobody anticipates”

Left alone, the router develops favourites, and the mechanism is a straightforward runaway.

Suppose expert 3 starts marginally better than the others by chance. The router sends it slightly more tokens. More tokens means more gradient updates, so it gets better faster. Being better, it attracts more tokens. Within a few thousand steps the router sends nearly everything to expert 3 and the remaining experts are dead weight — parameters that consume memory and never learn.

This is routing collapse, and it is not a rare failure; it is the default behaviour. Every MoE system carries machinery whose only job is to prevent it.

Tier 2 · Mechanics

How it actually works. Pseudocode, no heavy maths.

Where the experts go

Section titled “Where the experts go”

The routing loop

Section titled “The routing loop”

  1. Score. A single linear layer maps the token representation to NNN logits, one per expert. This is the entire router — a d×Nd \times Nd×N matrix, negligible in size.

  2. Select top-kkk. Usually k=2k=2k=2; Switch Transformer showed k=1k=1k=1 works and is cheaper, at some quality cost. DeepSeek-style models use larger kkk over many more, smaller experts.

  3. Dispatch. Send each token to its chosen experts. In a distributed setting experts live on different devices, so this is an all-to-all communication — and it is frequently the bottleneck, not the arithmetic.

  4. Compute and combine. Each expert applies its FFN; outputs are summed weighted by the (renormalised) routing probabilities.

Load balancing

Section titled “Load balancing”

The auxiliary loss that stops routing collapse. For NNN experts and a batch of TTT tokens, let fif_ifi​ be the fraction of tokens routed to expert iii and PiP_iPi​ the mean routing probability assigned to it. Then

Laux=α N∑i=1Nfi Pi.\mathcal{L}_{\text{aux}} = \alpha\, N \sum_{i=1}^{N} f_i \, P_i .Laux​=αNi=1∑N​fi​Pi​.

This is minimised when the load is uniform. The product form is deliberate: fif_ifi​ is a hard count and non-differentiable, PiP_iPi​ is soft and differentiable, so the gradient flows through PiP_iPi​ while fif_ifi​ supplies the actual imbalance signal.

α\alphaα is typically around 0.01. This term is in direct tension with the main objective — it pushes the router toward uniformity, which is precisely not what specialisation wants. Too large and experts fail to specialise; too small and the model collapses. DeepSeekMoE’s auxiliary-loss-free approach instead adds a learned per-expert bias to the routing logits, adjusted to equalise load without introducing a competing gradient — currently the more favoured design.

The capacity factor

Section titled “The capacity factor”

Hardware wants fixed-size tensors, so each expert gets a fixed buffer:

capacity=CF×T⋅kN,\text{capacity} = \text{CF} \times \frac{T \cdot k}{N},capacity=CF×NT⋅k​,

with CF\text{CF}CF the capacity factor, typically 1.0–1.25. Tokens arriving at a full expert are dropped — they skip the FFN entirely and pass through via the residual connection.

Token dropping is real and mostly invisible

A dropped token receives no FFN computation at that layer. With CF = 1.25 and imperfect balance this can affect a meaningful fraction of tokens. It is rarely reported, it degrades quality silently, and raising CF costs memory linearly. This is the practical reason load balancing matters as much as it does.

Design choices that differentiate real systems

Section titled “Design choices that differentiate real systems”
ChoiceOptionsTrade-off
Experts per token (kkk)1 (Switch), 2 (Mixtral), 8 (DeepSeek)more kkk = better quality, more FLOPs and communication
Expert count and sizefew large vs many smallmany small = finer specialisation, more routing overhead
Shared expertsnone vs always-on expert(s)shared experts absorb common knowledge so routed ones specialise
Routing directiontoken-choice vs expert-choiceexpert-choice guarantees balance but breaks causality
MoE layer placementevery layer vs every otheralternating reduces communication substantially

Expert-choice routing inverts the selection: instead of each token picking kkk experts, each expert picks its top-CCC tokens. Load is then perfectly balanced by construction and no auxiliary loss is needed. The catch is that a token’s routing now depends on the other tokens in the batch — fine for encoders, a causality violation for autoregressive decoding, which is why it has not become the default for LLMs.

The renormalisation over the selected set matters: without it the output magnitude scales with how confident the router happened to be, injecting a spurious signal into the residual stream.

Gradients. The top-kkk operation is not differentiable, but gradients still reach WgW_gWg​ through the gi(x)g_i(x)gi​(x) coefficients of the selected experts. Unselected experts receive no gradient at all from this token — which is the mathematical origin of the collapse dynamic. An expert that stops being selected stops learning entirely, and cannot recover on its own.

Shazeer et al.’s original fix was noisy top-kkk gating: add tunable Gaussian noise to the logits before selection,

H(x)i=(Wg⊤x)i+ε⋅softplus⁡((Wnoise⊤x)i),ε∼N(0,1),H(x)_i = (W_g^{\top}x)_i + \varepsilon \cdot \operatorname{softplus}\big((W_{\text{noise}}^{\top}x)_i\big), \qquad \varepsilon\sim\mathcal{N}(0,1),H(x)i​=(Wg⊤​x)i​+ε⋅softplus((Wnoise⊤​x)i​),ε∼N(0,1),

which gives losing experts a stochastic chance of selection — exploration, in the bandit sense.

paramsFLOPs  ∝  Nk.\frac{\text{params}}{\text{FLOPs}} \;\propto\; \frac{N}{k}.FLOPsparams​∝kN​.

With N=64N=64N=64 and k=2k=2k=2 you hold 32× the parameters for essentially the same per-token arithmetic. The router term dNdNdN is negligible — for d=4096d = 4096d=4096, N=64N=64N=64 that is 262k parameters against hundreds of millions per expert.

The efficiency claim, stated honestly. MoE models reach a given loss with fewer training FLOPs than dense models. They do not reach it with less memory, and they do not reach it with less total parameter storage — quite the opposite. The Switch Transformer result is a speedup in time to a given quality, which is the right metric for training and the wrong one for edge deployment.

Router z-loss

Section titled “Router z-loss”

A second auxiliary term, less discussed and important for stability:

Lz=1T∑x∈B(log⁡∑i=1Ne(Wg⊤x)i)2.\mathcal{L}_{z} = \frac{1}{T}\sum_{x\in\mathcal{B}} \left(\log \sum_{i=1}^{N} e^{(W_g^\top x)_i}\right)^{2}.Lz​=T1​x∈B∑​(logi=1∑N​e(Wg⊤​x)i​)2.

This penalises large router logits. Without it the logits grow, the softmax saturates, and the layer becomes numerically unstable in bf16 — a failure mode that shows up as loss spikes late in training. Cheap insurance, and its omission is a common cause of unexplained MoE training instability.

Tier 4 · Frontier

Open problems, current results, and what is still contested.

Where this stands, as of 2026

Section titled “Where this stands, as of 2026”

Sparse is the default at the frontier. Most large models released since 2024 are MoE. The reason is straightforward economics: for a fixed training budget and a fixed inference cost target, sparsity buys more capacity, and the engineering to make it work is now well understood.

Fine-grained experts with shared experts is the current best recipe. DeepSeekMoE’s design — split the FFN into many small experts, activate more of them, and keep one or two always-on “shared” experts — outperforms the classic few-large-experts layout at matched compute. The argument is that shared experts absorb the knowledge every token needs, freeing routed experts to actually specialise rather than each re-learning the common case.

Auxiliary-loss-free balancing is displacing the auxiliary loss. Adjusting per-expert routing bias to equalise load, rather than adding a competing gradient term, avoids the tension with the main objective. This is a clear improvement and is being adopted broadly.

“Experts” remains a misnomer. Analyses of routing in Mixtral and elsewhere found routing correlates strongly with syntactic and token-level features and weakly with semantic domain. There is no physics expert. The specialisation is real but operates at a level well below what the name suggests, and papers continue to use the name anyway.

Open problems

Section titled “Open problems”

  • Scaling laws for MoE are immature. Chinchilla tells you how to trade parameters against tokens for dense models. The sparse equivalent has extra axes — expert count, kkk, granularity — and no comparably clean result.

  • Inference is awkward. Batched serving works well because different tokens hit different experts and the load averages out. Single-stream inference does not: you pay full memory for one token’s worth of compute. Expert offloading and caching help and add latency.

  • Fine-tuning MoE models is unreliable. Routing shifts during fine-tuning, sometimes collapsing on small datasets. The interaction between LoRA-style adaptation and routing is poorly characterised.

  • Nobody can predict what an expert will learn. Routing patterns are emergent and not controllable, which blocks the obvious applications — you cannot ask for a medical expert and get one.

  • Communication dominates at scale. All-to-all dispatch across devices is frequently the bottleneck. This is a systems problem constraining a modelling choice, and it shapes which configurations are practical more than quality considerations do.
