<Abstract>
An agent is a language model in a loop with tools and a stopping condition. That
is the entire architecture — the difficulty is not building the loop but making
it survive twenty iterations without compounding its own errors. Per-step
reliability of 95% gives you 36% success over twenty steps, and that arithmetic,
more than any capability limit, is what determines where agents work today.
</Abstract>

<KeyPoints>

- **Tool use converts generation into verification.** A model asked to compute $\sqrt{18327}$ must produce digits from a distribution; a model that calls a calculator gets the answer. Prefer tools wherever a correct external answer exists.
- **The binding constraint is error compounding, not intelligence.** $0.95^{20} \approx 0.36$. Long-horizon reliability requires either a very high per-step success rate or a mechanism that catches and corrects failures.
- **Reasoning before acting measurably helps, and reasoning alone hallucinates.** ReAct's contribution was interleaving them: thoughts keep the plan coherent, observations keep it grounded. Either without the other degrades.
- **Evaluating agents is harder than evaluating models.** The same task can succeed via different trajectories, runs are stochastic, and a single number hides whether the agent got lucky. Report pass@1 across multiple seeds, not a best run.

</KeyPoints>

<Tier level="intuition" />

## The loop

Strip away the terminology and an agent is four steps repeated:

<Steps>

1. The model looks at the goal and everything that has happened so far.
2. It decides on one action — call a tool, or declare it is finished.
3. The action runs, in the world, and returns a result.
4. The result is appended to the history. Go to 1.

</Steps>

That is all. A chatbot is this loop with zero iterations and no tools. Everything
labelled "agentic" is a variation on how step 2 chooses, and how you decide when
to stop.

## Why tools beat memory

Ask a model for the current time and it cannot know — it is generating text, not
reading a clock. Ask it to multiply two large numbers and it will produce
digit-by-digit output from a learned distribution, which is right surprisingly
often and not reliably.

Give it a clock and a calculator and both problems dissolve. **The model's job
changes from knowing the answer to knowing which tool answers the question.** That
second job is much easier and much more reliable.

The generalisation is worth holding: a tool is worth adding whenever a correct
answer exists outside the model and the model's own attempt would be a guess.

## The arithmetic that governs everything

Suppose an agent is right 95% of the time at each step. That sounds excellent.

Over a twenty-step task, if any single failure derails the run:

$$
0.95^{20} \approx 0.36 .
$$

**Thirty-six percent.** At 99% per step it is 82%. At 90% it is 12%.

This is why agents work well on short, well-scoped tasks and struggle on long
open-ended ones — and why the useful engineering questions are "how do we shorten
the horizon?" and "how do we make failures recoverable?" rather than "how do we
make the model smarter?".

<Aside type="tip" title="The two levers, and they are not equal">
You can raise per-step reliability, or you can make failures **recoverable** so
they do not terminate the run. The second is usually the better investment: a tool
that returns a clear error the model can act on turns a fatal step into a retry,
which changes the exponent's base far more than a marginally better prompt does.
</Aside>

## The patterns

<Tabs>
<TabItem label="ReAct">

Interleave **Thought → Action → Observation**, repeatedly.

The paper's contribution was showing that either half alone underperforms.
Chain-of-thought reasoning without actions hallucinates facts — nothing grounds
it. Actions without reasoning lose the thread across steps — the model has no
place to maintain a plan.

Together, thoughts carry the plan forward and observations correct it. This is
the substrate almost every production agent still runs on, and it long predates
the tooling built around it.

</TabItem>
<TabItem label="Reflexion">

After a failed attempt, have the model write a **verbal** post-mortem — what went
wrong, what to do differently — and put that text in the context for the next
attempt.

The framing worth noticing: this is reinforcement learning where the "policy
update" is natural language in the context window rather than a gradient step. No
weights change. The lesson persists only as long as the text stays in context.

It works, and it depends entirely on the model producing an accurate diagnosis of
its own failure — which it often cannot, particularly when the failure was a
misreading rather than a mistake.

</TabItem>
<TabItem label="Search over plans">

Tree of Thoughts generalises chain-of-thought from a single line to a **tree**:
generate several candidate next steps, evaluate them, expand the promising ones,
backtrack from dead ends.

This is classical search with the model supplying both the successor function and
the heuristic. It helps substantially on puzzle-like tasks with verifiable
intermediate states, and costs many times more tokens.

Self-consistency is the cheap relative: sample several independent
chain-of-thought traces and take the majority answer. It requires no tree, no
evaluator, and captures a large share of the benefit when the answer space is
small.

</TabItem>
<TabItem label="Tool interfaces">

Tools are exposed to the model as typed function signatures with descriptions. The
model emits a structured call; the runtime executes it and returns the result.

**The description is a prompt, and it is usually the weakest link.** Most tool-use
failures in practice are not reasoning failures — they are the model calling the
wrong tool because two descriptions overlap, or passing a malformed argument
because the schema was ambiguous. Tool design deserves the same care as prompt
design, and gets far less.

The Model Context Protocol standardises this interface so tools are portable
across clients rather than reimplemented per application.

</TabItem>
</Tabs>

## Practical guards

| Failure | Guard |
|---|---|
| Infinite loop on a failing action | hard iteration cap; detect repeated identical calls |
| Context exhaustion | summarise or evict old observations; keep the goal pinned |
| Irreversible side effect | require confirmation for destructive actions; prefer dry-run modes |
| Silent wrong answer | verify with a second tool where one exists |
| Cost runaway | token and wall-clock budget per run, enforced by the runtime |

Almost all of these are runtime concerns rather than model concerns, which is the
general shape of agent engineering: **the model is one component, and most
reliability comes from the scaffolding around it.**

## The loop as a POMDP

An agent is a partially observed decision process. At step $t$ the model holds a
history

$$
h_t = (g,\ a_1, o_1,\ a_2, o_2,\ \dots,\ a_{t-1}, o_{t-1}),
$$

with $g$ the goal, and samples an action from the policy induced by the LM:

$$
a_t \sim \pi_\theta(\cdot \mid h_t), \qquad o_t = \mathcal{E}(a_t),
$$

where $\mathcal{E}$ is the environment. Termination is itself an action.

Two structural properties distinguish this from standard RL:

**The history is the state, and it is unbounded.** There is no learned state
compression — everything is kept verbatim in the context. So the effective state
space grows with $t$, and eventually exceeds the window. Summarisation is a lossy
state-compression scheme bolted on, and what it discards is chosen heuristically.

**The policy is frozen.** No gradient flows. Within-episode adaptation happens
entirely through what is written into $h_t$ — which is exactly what Reflexion
exploits and exactly why its lessons vanish when the context is trimmed.

## Compounding reliability

Let $p$ be the probability a step succeeds, and assume failures are independent
and fatal. Success over $n$ steps:

$$
P_{\text{success}} = p^{n}.
$$

Solving for the per-step reliability needed to hit a target $P^*$:

$$
p \;=\; \big(P^{*}\big)^{1/n}.
$$

For $P^* = 0.9$ over $n=50$ steps, $p = 0.9^{1/50} \approx 0.9979$. **Better than
99.7% per step**, which is far beyond what current models achieve on open-ended
actions.

Now add recovery. If a failed step is retried and succeeds with probability $p$
each time, up to $k$ attempts, the effective per-step reliability is

$$
p_{\text{eff}} = 1 - (1-p)^{k},
$$

so at $p = 0.95$ and $k=3$, $p_{\text{eff}} = 1 - 0.05^3 = 0.999875$, and

$$
p_{\text{eff}}^{20} \approx 0.9975 .
$$

**Retry moves success from 36% to 99.7%.** This is the formal version of the
earlier claim that recoverability beats raw accuracy — and it holds only when
failures are *detectable* and *independent*, which is precisely what good tool
error messages and idempotent operations buy you. A failure the agent cannot see
is not retryable.

## Self-consistency

Sample $m$ independent reasoning traces and take the plurality answer:

$$
\hat y = \arg\max_{y}\ \sum_{i=1}^{m}\mathbb{1}\{y_i = y\}.
$$

Why this helps: reasoning errors are largely *independent* across samples while the
correct path is *systematic*. If each trace is correct with probability $p > 1/2$
and errors scatter across many distinct wrong answers, the majority converges on
the truth as $m$ grows — the Condorcet jury argument.

The condition matters. When errors are **correlated** — a systematic
misunderstanding of the question, a shared flawed assumption — the majority
converges on the wrong answer with increasing confidence. Self-consistency
amplifies agreement, and agreement is not evidence when the mistakes share a
cause.

## Test-time compute

The unifying frame for chain-of-thought, self-consistency, tree search, and
extended reasoning: they all spend more compute at inference to improve one
answer, rather than more compute at training to improve all answers.

$$
\text{quality} = f\big(\text{train compute},\ \text{test compute}\big),
$$

and the empirical finding since 2024 is that the second argument has been badly
under-exploited. DeepSeek-R1 showed RL on verifiable rewards induces models to
*lengthen their own reasoning* — the model discovers that thinking longer produces
correct answers, and the reward makes that discovery.

This connects agents to [post-training](/training/post-training/) directly: an
agent's loop is test-time compute with an environment attached, and RLVR is how
you train a model to use that compute well.

## Where this stands, as of 2026

**Agents work well when the task is verifiable and the horizon is short.** Coding
is the clearest case, and not by accident — tests provide ground truth at every
step, so failures are detectable and therefore recoverable. SWE-bench performance
climbed dramatically once models were trained with that loop in mind.

**Reasoning models changed the shape of the problem.** Models trained with RL on
verifiable rewards do substantially more of the planning internally, which reduces
how much scaffolding the surrounding framework must supply. Some of the elaborate
2023-era agent architectures are now unnecessary.

**Tool interfaces have standardised.** MCP established a common protocol for
exposing tools, so integrations are written once rather than per framework. This
is unglamorous and it is the change that most affects what people can actually
build.

**Multi-agent systems remain oversold.** Several specialised agents passing
messages sounds appealing and frequently underperforms one capable agent with good
tools. Each hand-off is a lossy serialisation of context, and the coordination
overhead usually exceeds the specialisation benefit. Treat multi-agent
architectures as something to justify, not to assume.

## Open problems

- **Long-horizon reliability is unsolved.** Everything above is mitigation. Tasks
  requiring hundreds of dependent steps remain out of reach, and the compounding
  arithmetic says why.

- **Evaluation is genuinely hard.** Trajectories vary between runs, multiple paths
  can be correct, and partial credit is ill-defined. A single reported success rate
  from one seed conveys very little. Report pass@1 over multiple seeds and, where
  possible, the trajectory cost.

- **Prompt injection is unmitigated.** An agent that reads untrusted content —
  web pages, emails, documents — can be instructed by that content. There is no
  robust defence, only partial ones, and this is the primary reason capable agents
  are deployed with narrow permissions.

- **Cost is unpredictable.** The same task can consume wildly different token
  counts across runs. Budgeting is guesswork, and this blocks a lot of production
  deployment.

- **Credit assignment across a trajectory is unsolved.** When a twenty-step run
  fails, which step was responsible? Without an answer, training agents end-to-end
  is extremely sample-inefficient.

## What to read next, in order

1. **Yao et al. (2022), ReAct** — the ablations showing reasoning-only and
   acting-only both underperform are the argument.
2. **Wang et al. (2022), Self-Consistency** — cheap, effective, and a good lesson

3. **Jimenez et al. (2023), SWE-bench** — read the task construction. It is the
   most honest agent benchmark and the construction explains why.
4. **DeepSeek-AI (2025), R1** — for how test-time compute is trained rather than
