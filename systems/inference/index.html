Inference and Serving

Generating one token requires reading every weight in the model from memory and doing almost no arithmetic with each. On an H100 that means the GPU is idle roughly 99% of the time, waiting on memory. Nearly every inference optimisation that matters is a response to this single fact — either move fewer bytes, or get more useful work out of the bytes you already moved.

What you should walk away with

  • Decoding is memory-bound; prefill is compute-bound. They are different workloads with different bottlenecks, and treating them as one problem is why naive serving is slow.
  • Arithmetic intensity is the number to compute. Batch size 1 decoding does ~2 FLOPs per byte read; an H100 wants ~300. That ratio is the whole story, and it is why batching is the single highest-leverage optimisation.
  • Quantization is a bandwidth optimisation first. 4-bit weights are 4× fewer bytes to move, so ~4× faster decoding. The memory saving is real; the speedup is the actual reason people do it.
  • Speculative decoding buys parallelism, not fewer FLOPs. A small model guesses several tokens, the large model verifies them in one pass. You spend more compute to use the bandwidth you were wasting — and the output distribution is provably unchanged.
Tier 1 · Intuition

Plain language. No equations, no prerequisites.

The GPU is not the bottleneck

Section titled “The GPU is not the bottleneck”

Here is the fact that reorganises everything.

To generate one token, the model reads every weight from GPU memory and multiplies each by a number. For a 70B model in fp16 that is 140 GB read. An H100 has about 3.35 TB/s of memory bandwidth, so the read alone takes roughly 42 milliseconds — about 24 tokens per second, and that is a hard ceiling.

Meanwhile the arithmetic — 140 billion multiply-adds — takes under a millisecond on hardware capable of ~1000 TFLOP/s.

The GPU spends 98% of its time waiting for memory. Buying a faster GPU with the same bandwidth changes nothing.

Two workloads wearing one name

Section titled “Two workloads wearing one name”

  1. Prefill. Process the prompt. All tokens go through at once, so you read each weight once and use it for hundreds of tokens. Compute-bound, efficient, fast.

  2. Decode. Generate token by token. Each token requires reading all the weights again, and uses each weight exactly once. Memory-bound, inefficient, slow.

A 1000-token prompt might prefill in 100ms and then generate 1000 tokens over 40 seconds. Almost all the time is in the slow phase, which is why “time to first token” and “tokens per second” are reported separately — they measure different bottlenecks and different optimisations fix them.

Why batching is the biggest win

Section titled “Why batching is the biggest win”

If you read 140 GB of weights to serve one user, and a second request arrives, you can serve both from the same read. The weights are already in registers; using them twice costs almost nothing extra.

Batch 32 requests and you read the weights once for 32 tokens instead of 32 times. Throughput goes up nearly 32×, with only a small increase in latency per request.

This is why hosted inference is cheap and local inference is not. A server batching hundreds of concurrent requests operates in a fundamentally more efficient regime than your laptop generating one stream.

What every technique on this page is doing

Either move fewer bytes (quantization, GQA, KV-cache compression) or get more work per byte moved (batching, speculative decoding). There is no third category. Once you have that frame, each technique’s benefit and limits are predictable.

The KV cache

Section titled “The KV cache”

Attention needs keys and values for all previous tokens. Recomputing them each step would be quadratic waste, so they are cached — and the cache becomes the dominant memory consumer at long context.

KV bytes=2×L×nlayers×nkv-heads×dhead×bytes/elem.\text{KV bytes} = 2 \times L \times n_{\text{layers}} \times n_{\text{kv-heads}} \times d_{\text{head}} \times \text{bytes/elem}.KV bytes=2×L×nlayers​×nkv-heads​×dhead​×bytes/elem.

For a 70B-class model (80 layers, 8 KV heads after GQA, dhead=128d_{\text{head}}=128dhead​=128) in fp16 at 100k tokens:

2×100,000×80×8×128×2≈32 GB2 \times 100{,}000 \times 80 \times 8 \times 128 \times 2 \approx 32\ \text{GB}2×100,000×80×8×128×2≈32 GB

per sequence. Without GQA (64 heads) that would be 256 GB — larger than the model. GQA is primarily a serving optimisation, and this calculation is why.

The four levers

Section titled “The four levers”
  • Quantization
  • Speculative decoding
  • PagedAttention
  • Batching

Store weights in fewer bits. 4-bit instead of 16-bit means 4× fewer bytes to read, so roughly 4× faster decoding — the speedup comes from bandwidth, not from cheaper arithmetic.

GPTQ quantises layer by layer, minimising the error in that layer’s output rather than in its weights, using second-order (Hessian) information to decide rounding. Weights whose perturbation matters more get rounded more carefully.

AWQ starts from a different observation: a small fraction of weights — roughly 1% — matter disproportionately, and which ones can be identified from activation magnitudes rather than weight magnitudes. Scale those channels up before quantising so they survive, then scale back. No backprop required, so it is fast and it generalises across calibration sets better.

The rule of thumb: 8-bit is essentially lossless. 4-bit costs a small, measurable amount of quality. Below 4-bit, degradation becomes serious except with specialised methods.

Use a small fast model to draft γ\gammaγ tokens, then have the large model verify all γ\gammaγ in a single forward pass — the same pass that would have produced one token.

Why this is free-ish: verifying γ\gammaγ tokens costs the same weight read as producing one, because you read the weights once regardless. You are converting wasted bandwidth into speculative compute.

Accepted tokens are kept; at the first rejection you resample from a corrected distribution and discard the rest. Typical speedups are 2–3×.

The output distribution is provably identical to standard sampling. This is the property that makes it usable in production — it is not an approximation, and enabling it cannot change your model’s behaviour.

The insight behind vLLM, borrowed directly from operating systems.

Naive serving allocates a contiguous KV buffer sized to the maximum sequence length for every request. A request that generates 100 tokens in a 4096-token buffer wastes 97.5% of it. Measured waste in real systems was 60–80%.

PagedAttention stores the KV cache in fixed-size blocks that need not be contiguous, with a block table mapping logical positions to physical blocks — virtual memory, applied to attention. Waste drops to under 4%.

The second benefit is sharing. Two requests with the same prompt prefix can point at the same physical blocks, with copy-on-write on divergence. For chat with a long shared system prompt, or parallel sampling from one prompt, this is a large saving.

Static batching waits for a full batch, runs it to completion, returns. The whole batch is held hostage by its longest sequence — finished slots sit idle.

Continuous batching operates at the iteration level: when a sequence finishes, a queued request takes its slot immediately. GPU utilisation stays high and reported throughput improvements are large — often several-fold over static batching at the same latency target.

This, combined with PagedAttention, is most of what modern serving engines do.

Tier 4 · Frontier

Open problems, current results, and what is still contested.

Where this stands, as of 2026

Section titled “Where this stands, as of 2026”

Continuous batching plus PagedAttention is table stakes. Every serious serving stack implements both. The differentiation has moved to scheduling policy, prefix-cache management, and disaggregation.

Prefill/decode disaggregation is the current architectural shift. Since the two phases have opposite bottlenecks, running them on separate hardware pools — compute-dense for prefill, bandwidth-dense with more memory for decode — lets each be provisioned appropriately and prevents long prefills from stalling decode batches.

4-bit is the practical floor for weights. GPTQ and AWQ at 4-bit are near- lossless for most uses. Below that, quality degrades sharply without specialised methods, and the marginal bandwidth saving shrinks anyway.

KV cache quantization is the newer frontier. Weights are well-handled; the cache is now often the larger consumer at long context. 8-bit KV is near-lossless; 4-bit is usable with per-channel scaling. Attention sinks — the observation that the first few tokens absorb disproportionate attention mass and must be preserved at higher precision — matter here.

Speculative decoding has broadened. Beyond a separate draft model: self- speculation using early layers, Medusa-style multiple prediction heads, and n-gram lookup from the prompt (very effective for code, where verbatim repetition is common). All share the same correctness guarantee.

Open problems

Section titled “Open problems”

  • Long-context serving remains hard. The KV cache grows linearly and attention cost grows with context. Eviction, compression, and offloading all trade quality or latency, and none is clearly right.

  • Latency/throughput scheduling is unsolved. Larger batches raise throughput and raise per-request latency. Optimal scheduling under mixed SLAs is an open systems problem, currently handled with heuristics.

  • Quantization interacts badly with fine-tuning and MoE. Quantised MoE models can shift routing; quantised fine-tuned models sometimes degrade disproportionately. The interactions are not well characterised.

  • Speculative decoding is worthless at large batch. Its benefit comes from spare bandwidth, and at large batch there is none. The techniques that help single-stream latency and those that help server throughput are largely disjoint, which is under-appreciated.

  • Evaluating quantized models is done badly. Perplexity is insensitive to degradations that show up on reasoning and long-context tasks. Reported “lossless” claims frequently rest on perplexity alone.
