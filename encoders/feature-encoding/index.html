Feature Encoding

Models consume numbers; a lot of real data is words. Feature encoding is the translation step, and it is the least glamorous and most consequential part of applied tabular ML. The methods have been stable for twenty years. What is not stable is practitioners’ handling of target encoding, which leaks the label into the features unless computed inside a cross-validation fold — producing models that validate at 0.95 AUC and fail in production. That single failure mode is the reason this page exists.

What you should walk away with

  • The only question that matters first is cardinality. Under ~15 categories, one-hot and stop thinking. Over a few thousand, one-hot is not an option and the interesting trade-offs begin.
  • Ordinal encoding asserts an ordering. Encoding {red, green, blue} as {0,1,2} tells a linear model that green sits between red and blue. If that is false, you have injected a lie into your features, and tree models will happily exploit it.
  • Target encoding is the strongest method and the most dangerous. It leaks by construction. Computed correctly — out-of-fold, inside the pipeline — it is excellent. Computed on the full dataset, it produces a model that has memorised the answer.
  • Tree models and linear models want different encodings. Gradient-boosted trees handle ordinal integers fine and are hurt by one-hot’s sparsity; linear models are the reverse. Choosing an encoding without knowing the model is choosing blind.
Tier 1 · Intuition

Plain language. No equations, no prerequisites.

The problem

Section titled “The problem”

You have a table. One column is city, with values like London, Mumbai, São Paulo. Your model does arithmetic. London is not a number.

So you need a rule for turning cities into numbers. The obvious rule — number them 1, 2, 3 in alphabetical order — creates a problem that is easy to miss: you have just told the model that Mumbai is between London and São Paulo, and that São Paulo is three times London. Neither statement means anything. A linear model will take both entirely seriously.

Feature encoding is the study of rules that don’t accidentally assert things you didn’t mean.

The trap, stated before you can fall into it

Section titled “The trap, stated before you can fall into it”

Target encoding replaces each category with the average outcome for that category. London → 0.31 means “31% of London rows were positive”.

Consider a category that appears exactly once, in a row where the label is 1. Its target encoding is 1.0. The feature now contains the label for that row. Your model does not need to learn anything — it can read the answer off the feature. Validation accuracy will look extraordinary. Production accuracy will be chance.

This is the single most common serious bug in applied tabular ML

If you compute target encoding on your full dataset and then split into train and test, every fold is contaminated. The fix is not optional and not subtle: compute the encoding using only the training portion, inside the cross-validation loop. In scikit-learn terms, it must be a step in a Pipeline, never a transformation applied to the dataframe beforehand.

Tier 2 · Mechanics

How it actually works. Pseudocode, no heavy maths.

Choosing: a procedure

Section titled “Choosing: a procedure”

  1. Count the distinct values. This single number drives most of the decision.

  2. Under ~15 categories → one-hot. It is unambiguous, it makes no false assertions, and the dimensional cost is negligible. Do not overthink it.

  3. 15 to a few thousand → depends on your model. Gradient-boosted trees: native categorical handling if available (LightGBM, CatBoost), otherwise ordinal. Linear or neural: target encoding done properly, or learned embeddings.

  4. Genuinely ordered categories (small < medium < large, bronze < silver < gold) → ordinal, with the codes reflecting the real order. This is the one case where ordinal is not a lie, and it is strictly better than one-hot because it hands the model a fact it would otherwise have to learn.

  5. Tens of thousands or more (user IDs, URLs, product SKUs) → hashing if you need a fixed memory budget and streaming; learned embeddings if you have a neural model and enough data per category.

  6. Unseen categories at inference time → hashing handles this natively; everything else needs an explicit unknown bucket, decided in advance.

Model-dependence, which people skip

Section titled “Model-dependence, which people skip”

The right encoding depends on what consumes it, and the two dominant model families want opposite things.

Linear / neuralGradient-boosted trees
One-hotgood — each category gets its own weightpoor — sparse binary splits waste tree depth
Ordinalbad — imposes a false linear relationshipfine — trees split on thresholds, order is largely irrelevant
Targetgoodgood — often the strongest option
Embeddingsbest, learned jointlynot applicable directly

The one-hot-hurts-trees result surprises people. The reason: a tree splitting on a one-hot column can only ask “is it London or not?”, so isolating one of 100 categories takes up to 100 sequential splits, and each split sees fewer samples than the last. Native categorical handling asks “is it in {London, Paris, Berlin}?” in a single split.

Regularising target encoding

Section titled “Regularising target encoding”

Raw category means are unusable for rare categories — one observation gives you a mean of 0 or 1 with no reliability. The standard fix is smoothing toward the global mean, with the weight determined by how much data the category has:

y^c=nc⋅yˉc+m⋅yˉnc+m,\hat{y}_c = \frac{n_c \cdot \bar{y}_c + m \cdot \bar{y}}{n_c + m},y^​c​=nc​+mnc​⋅yˉ​c​+m⋅yˉ​​,

where ncn_cnc​ is the count for category ccc, yˉc\bar{y}_cyˉ​c​ its mean, yˉ\bar{y}yˉ​ the global mean, and mmm a smoothing constant. A category seen once is pulled almost entirely to the global mean; a category seen ten thousand times keeps its own.

This is Micci-Barreca’s 2001 scheme and it remains the standard. But note what it does not fix: smoothing reduces variance, it does not remove leakage. You still need out-of-fold computation.

The objective, the equations, the guarantees.

One-hot and the dummy-variable trap

Section titled “One-hot and the dummy-variable trap”

One-hot maps c∈{1,…,k}c \in \{1,\dots,k\}c∈{1,…,k} to ec∈{0,1}ke_c \in \{0,1\}^kec​∈{0,1}k. Distances are uninformative by construction:

∥ei−ej∥2=2for all i≠j.\|e_i - e_j\|_2 = \sqrt{2} \quad \text{for all } i \neq j.∥ei​−ej​∥2​=2​for all i=j.

Every pair of categories is equidistant. This is exactly right when you have no prior similarity information, and exactly wrong when you do — it is why one-hot cannot express that London and Manchester are more alike than London and Mumbai.

The dummy-variable trap. The kkk columns are linearly dependent — they sum to the all-ones vector. With an intercept, the design matrix is rank-deficient and X⊤XX^{\top}XX⊤X is singular, so ordinary least squares has no unique solution. Drop one column (drop_first=True) to restore full rank.

Two important caveats on that advice, both routinely mishandled:

  • With ℓ2\ell_2ℓ2​ regularisation, do not drop. Ridge already handles the singularity, and dropping a level makes the penalty asymmetric across categories — the dropped level is treated differently from the rest for no principled reason.
  • For tree models, never drop. There is no matrix inversion, and dropping a level simply hides a category from the splitter.

Ordinal encoding, formally

Section titled “Ordinal encoding, formally”
ϕord(c)=π(c),π:{1,…,k}→{0,…,k−1}.\phi_{\text{ord}}(c) = \pi(c), \qquad \pi: \{1,\dots,k\} \to \{0,\dots,k-1\}.ϕord​(c)=π(c),π:{1,…,k}→{0,…,k−1}.

For a linear model f(x)=w ϕord(c)+bf(x) = w\,\phi_{\text{ord}}(c) + bf(x)=wϕord​(c)+b, the encoding constrains the fitted effects to be collinear in the assigned order:

f(ci+1)−f(ci)=wfor all i,f(c_{i+1}) - f(c_i) = w \quad \text{for all } i,f(ci+1​)−f(ci​)=wfor all i,

i.e. the model is forced to believe every adjacent pair of categories differs by the same amount. When the ordering is real and roughly evenly spaced, this is a useful constraint that saves parameters. When it is arbitrary, it is a misspecification the model cannot escape.

For trees the situation is different but not harmless. A tree can carve {0,…,k−1}\{0,\dots,k-1\}{0,…,k−1} into arbitrary intervals, so it can recover any grouping that is contiguous in π\piπ. Groupings that are not contiguous require multiple splits. So the arbitrary ordering does not make the model wrong, but it does make some groupings cheaper to express than others — a real, if mild, inductive bias you did not intend.

Target encoding and the leakage bound

Section titled “Target encoding and the leakage bound”
ϕtgt(c)=E[Y∣C=c],estimated asϕ^(c)=1nc∑i:ci=cyi.\phi_{\text{tgt}}(c) = \mathbb{E}\big[Y \mid C = c\big], \quad \text{estimated as} \quad \hat{\phi}(c) = \frac{1}{n_c}\sum_{i : c_i = c} y_i .ϕtgt​(c)=E[Y∣C=c],estimated asϕ^​(c)=nc​1​i:ci​=c∑​yi​.

Consider the contribution of row iii to its own encoded value. Decompose:

ϕ^(ci)=yinc+nc−1nc⋅ϕ^−i(ci),\hat{\phi}(c_i) = \frac{y_i}{n_c} + \frac{n_c - 1}{n_c}\cdot \hat{\phi}_{-i}(c_i),ϕ^​(ci​)=nc​yi​​+nc​nc​−1​⋅ϕ^​−i​(ci​),

where ϕ^−i\hat{\phi}_{-i}ϕ^​−i​ excludes row iii. The first term is direct label leakage, and its magnitude is 1/nc1/n_c1/nc​. So:

  • nc=1n_c = 1nc​=1: the feature is the label. Complete leakage.
  • nc=10n_c = 10nc​=10: 10% of the feature value is the row’s own label.
  • nc=10 000n_c = 10\,000nc​=10000: negligible.

Leakage severity is inversely proportional to category frequency — which is why the problem is worst exactly where target encoding is most attractive, on high-cardinality columns with long tails.

The correct estimator is the leave-one-out or, better, out-of-fold version:

ϕ^OOF(ci)=1∣Sc ∖k(i)∣∑j∈Sc ∖k(i)yj,\hat{\phi}^{\text{OOF}}(c_i) = \frac{1}{|\mathcal{S}_{c}^{\,\setminus k(i)}|} \sum_{j \in \mathcal{S}_{c}^{\,\setminus k(i)}} y_j,ϕ^​OOF(ci​)=∣Sc∖k(i)​∣1​j∈Sc∖k(i)​∑​yj​,

computed from folds other than the one containing row iii. CatBoost goes further with ordered target statistics: impose a random permutation and encode each row using only rows earlier in that permutation, which mimics a time-ordered stream and removes the leakage exactly rather than approximately.

Leave-one-out is not as safe as it looks

Plain LOO target encoding removes the direct term but introduces a subtler problem: for a binary target within a small category, the LOO value is a deterministic decreasing function of yiy_iyi​. A tree can invert it. Ordered target statistics or proper K-fold OOF are the safe options; LOO is not.

Feature hashing

Section titled “Feature hashing”
ϕhash(c)j=∑c′:h(c′)=jξ(c′),h:C→{1,…,b},ξ:C→{±1}.\phi_{\text{hash}}(c)_j = \sum_{c' : h(c') = j} \xi(c'), \qquad h: \mathcal{C} \to \{1,\dots,b\}, \quad \xi: \mathcal{C} \to \{\pm 1\}.ϕhash​(c)j​=c′:h(c′)=j∑​ξ(c′),h:C→{1,…,b},ξ:C→{±1}.

The signed variant ξ\xiξ is the part that makes the guarantee work. Weinberger et al. showed the hashed inner product is unbiased:

E[⟨ϕhash(x),ϕhash(x′)⟩]=⟨x,x′⟩,\mathbb{E}\big[\langle \phi_{\text{hash}}(x), \phi_{\text{hash}}(x') \rangle\big] = \langle x, x' \rangle,E[⟨ϕhash​(x),ϕhash​(x′)⟩]=⟨x,x′⟩,

because collisions contribute +1+1+1 and −1-1−1 with equal probability and cancel in expectation. Without the signs, collisions would add and the inner product would be systematically inflated.

Collision probability for kkk categories in bbb buckets is approximately 1−e−k2/2b1 - e^{-k^2/2b}1−e−k2/2b — the birthday bound. Practical consequence: to keep pairwise collisions rare you need bbb substantially larger than k2k^2k2, which is often infeasible. In practice one accepts collisions and relies on the unbiasedness, and the resulting model is genuinely worse than a collision-free encoding — hashing buys memory and streaming capability at a real accuracy cost.

Learned embeddings

Section titled “Learned embeddings”
ϕemb(c)=Ec,E∈Rk×d,d≪k,\phi_{\text{emb}}(c) = E_c, \qquad E \in \mathbb{R}^{k \times d}, \quad d \ll k,ϕemb​(c)=Ec​,E∈Rk×d,d≪k,

with EEE trained by backpropagation alongside the model. Since the embedding layer is a matrix multiply against a one-hot vector, this is exactly a one-hot encoding followed by a linear layer — the difference is that the linear layer is learned end-to-end, so it discovers a similarity structure that one-hot alone cannot express.

A common heuristic for dimensionality, from the entity-embeddings literature and the fast.ai defaults:

d=min⁡(600,  ⌈1.6⋅k0.56⌉).d = \min\big(600,\; \lceil 1.6 \cdot k^{0.56} \rceil\big).d=min(600,⌈1.6⋅k0.56⌉).

Treat this as a starting point, not a result — it is empirical folklore, widely used, with no theoretical backing.

The real requirement is data. Each category needs enough occurrences for its row of EEE to receive meaningful gradient. Categories appearing a handful of times end up with essentially random vectors, which is worse than target encoding’s smoothed estimate for those same categories. Embeddings are the best method when data is plentiful per category and among the worst when it is not.

Tier 4 · Frontier

Open problems, current results, and what is still contested.

Where this stands, as of 2026

Section titled “Where this stands, as of 2026”

The methods are settled; the practice is not. Nothing fundamental has changed since roughly 2017. What has changed is tooling: scikit-learn added a native TargetEncoder with internal cross-fitting in 1.3, which makes the safe path the default path for the first time. That is a bigger deal for real-world model quality than any new method would be.

Native categorical handling has largely won for trees. LightGBM and CatBoost handle categorical features internally, using approaches that are both more accurate and less error-prone than manual preprocessing. If you are using gradient-boosted trees on tabular data in 2026, the default advice is to use the library’s native support and not encode manually at all.

Tabular foundation models are the live question. Approaches that pretrain a transformer across many tables and treat categorical values as text tokens sidestep the encoding question entirely — the model reads London as a string. On small datasets these are competitive with tuned gradient boosting. Whether they displace the classical pipeline at scale is genuinely unsettled, and I would not bet either way yet.

Open problems

Section titled “Open problems”

  • Extreme cardinality is unsolved. A column with millions of categories and a heavy tail defeats every method here: hashing collides badly, target encoding’s leakage scales as 1/nc1/n_c1/nc​ and the tail has ncn_cnc​ of one or two, embeddings starve. This is the norm for user and item IDs in recommendation, and it is handled by domain-specific hacks rather than by any general method.

  • No principled dimensionality rule for embeddings. The 1.6k0.561.6 k^{0.56}1.6k0.56 heuristic is folklore. There is no derivation and no dataset-dependent theory.

  • Encoding choice is not part of model selection. It is treated as preprocessing and tuned by hand, when it interacts strongly with model family, regularisation, and cardinality. Joint search over encoding and model is rare and expensive.

  • Concept drift in target encodings is under-addressed. A target encoding is a statistic of the training distribution. When category-level base rates shift — which they do, constantly, in production — the encoding silently becomes wrong, and nothing in the standard pipeline detects it.
